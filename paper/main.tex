\title{Graph-Native Path Finding as a Loadable Extension: An MVCC-Consistent CSR Index for a Relational Engine}

\author{Daniel ten Wolde}
\affiliation{%
  \institution{CWI}
  \city{Amsterdam}
  \country{The Netherlands}
}
\email{dljtw@cwi.nl}

\begin{abstract}
SQL:2023 brought graph pattern matching into SQL. The shortest path is the part of it that relational systems
execute badly. In \duckpgq we answered it with multi-source BFS inside scalar UDFs, which inherit \duckdb's
parallelism for free. They also inherit its limit. A UDF receives work per tuple, so a single path pattern runs on one
core, and the compressed sparse row (CSR) representation of the graph is rebuilt for every query. This paper removes
both limits and remains a loadable extension. A path-finding operator with its own inputs and event schedule draws its
parallelism from a partitioned CSR, uses a multi-source traversal for many pairs and a frontier traversal for few,
and is reached from \sqlpgq's \texttt{MATCH} through an optimizer rule. A CSR index keeps the representation across
queries, restarts and checkpoints behind \duckdb's general index interface. That interface reports which rows changed
and nothing about which transactions may see them, so the index stores immutable epochs and a change log that \duckdb's own
row-version check classifies once per commit, and every reader traverses exactly the edges its transaction may see.
On LDBC SNB at scale factor 300, against Kuzu, Neo4j, Memgraph and FalkorDB, \duckpgq answers a single pair in
9\,ms where Kuzu needs 33\,ms and Neo4j 15\,ms, and 65\,536 pairs in 55\,s where both exceed ten minutes, because
they search once per pair and \duckpgq once per traversal. Under a stream of 2000 edge updates per commit at scale
factor 10 it answers a single-source query in 19\,ms and applies a commit in 9\,ms; Kuzu needs 16 and 342\,ms.

\end{abstract}
