\section{The Path-Finding Operator}
\label{sec:operator}

% Restructured 29 Oct 2026 against the rc7 code (eval-freeze-rc7) and the vocabulary in paper/STYLE.md. Build costs
% from eval-freeze-rc1; the traversal crossovers are single runs before the rerun and marked.

A path pattern in \sqlpgq asks, for a set of candidate (source, destination) pairs, whether a path of the allowed
length exists and how long it is, or which vertices and edges it uses. The path-finding operator evaluates this part of
the pattern. Label tests, filters on the source and destination vertices, the join back to the vertex tables and the
test on the quantifier stay relational and are left to \duckdb's planner. The operator reads the candidate pairs and
the graph, either as the edge table, from which it builds a CSR inside the query, or as a CSR index.

The operator answers in one of three modes. In the \emph{lengths} mode it returns one hop count per candidate pair,
and in the \emph{paths} mode one list of vertices and edges per pair. The \emph{reach} mode is for a pattern whose
destination has no condition, such as every person reachable from a given one. Listing every vertex as a candidate
destination would produce one pair per vertex. In the reach mode the operator therefore receives only the sources and
returns each vertex a source reaches, with its distance, and the destinations come out of the operator. The operator is opt-in through the setting \texttt{experimental\_path\_finding\_operator}; without it the
rewrite emits the UDF calls of the CIDR design. Unless stated otherwise, the numbers in this section are from the
evaluation of Section~\ref{sec:eval} (LDBC SNB \texttt{Person\_knows\_Person}, one m7a.8xlarge, 32 threads).

\subsection{From \texttt{MATCH} to an operator}
\label{sec:planner}

\duckpgq rewrites \texttt{MATCH} into SQL, and the path pattern becomes a scalar function call in that SQL. We call it
the \emph{marker}. It takes the source and destination columns of the candidate pairs, the edges as a struct column of
(source, destination) row ids, the vertex and edge counts, a constant key naming the graph, and the upper bound of the
quantifier. The function the marker calls names the mode. The rewrite asks for lengths when the query projects
\texttt{path\_length(p)}, for paths when it projects \texttt{vertices(p)}, \texttt{edges(p)} or
\texttt{element\_id(p)}, and for reach when the destination carries no condition. The marker is registered as a volatile scalar function so that no
part of \duckdb folds or reorders it, and it is never executed. An optimizer extension runs before \duckdb's own
optimizer, finds the projection that contains the marker, replaces the marker by a reference to the operator's output
column, and places a logical path-finding operator beneath the projection, with the pairs as its first child and, when
the CSR is built in the query, the edges as its second. The rule runs on the binder's plan shape, before join
reordering, because the two inputs are easy to identify there and hard to find after the optimizer has pushed filters
into them.

Three details of the rewrite matter for performance. First, the filters on the source and destination vertices are
applied to each vertex set before the two are combined. A query with one source and a selective filter on the
destination therefore yields few candidate pairs, and the unfiltered cross product of the vertex tables is never
formed.
Second, the upper bound of the quantifier travels with the marker, so a search stops at that depth instead of
exploring paths that a filter would discard afterwards. Third, when a CSR index exists for the edge table at bind
time, the rewrite drops the edge input and passes the index name in the key. The operator then resolves the key to a
snapshot (Section~\ref{sec:index}), and the pairs carry vertex keys instead of row ids, because the index identifies
vertices by key.

In \duckdb's execution model the physical operator is a sink for the pipelines of its children and the source of
the pipeline above it. Its first child produces the candidate pairs. When the CSR is built inside the query, a second
child produces the edges, the join of the edge table with its two vertex tables, as (source row id, destination row
id) pairs. Each of \duckdb's threads pushes vectors from these pipelines into a local state of its own; the pairs
are appended to a column collection, and the edges are partitioned as they arrive (Section~\ref{sec:csr}). When the
last vector is in, the operator's finalize step runs once. It translates the pairs to vertex ids, groups them by
source, picks the traversal and the orientation (Section~\ref{sec:choice}), and schedules the events that build the
CSR and traverse it (Sections~\ref{sec:traversals} and~\ref{sec:phases}). Once those events are done,
\duckdb starts the pipeline that reads the operator as its source, and that pipeline emits the results in parallel
(Section~\ref{sec:results}). The planner sees an operator with one or two children and a cardinality and plans the
rest of the query around it. The rest of this section follows a query through these steps.

\subsection{The partitioned CSR}
\label{sec:csr}

Both routes traverse the same layout, the \emph{partitioned CSR} of Figure~\ref{fig:partitioned-csr}. Vertices are
numbered $0$ to $V-1$; on the build route the number is the vertex's row id, on the index route the id the index's
dictionary gives its key. The vertex ids are cut into destination ranges of at most 65,535 ids, and a
\emph{partition} holds every edge whose destination falls into one range. Inside a partition the edges are grouped by
source into \emph{sparse rows}. Only a source with at least one edge into the range has a row, which holds the source
id and the offset of its edges, and each edge stores its destination as a 16-bit offset into the range. A
\emph{source index} over the rows is keyed by the high bits of the source id; a lookup of one source reads one entry
of it and then scans about two rows. When paths are asked for, and always in an index, every edge
position also carries the edge's row id. A partition can be built in the reverse direction too, holding the edges by
their source range, grouped by destination; an index stores these reverse partitions when it is created with
\texttt{WITH (reverse = true)}, and for an undirected graph the forward partitions serve both directions.

The traversals rely on two properties of the layout. A traversal step that processes partition $p$ writes only to
vertices of range $p$, and tasks that each own a partition therefore never write the same vertex; the multi-source
traversal splits its work this way (Section~\ref{sec:traversals}). And the memory is proportional to the edges,
because a destination takes 16 bits and no array has one entry per vertex.

\paragraph{Building it inside the query.} Without an index the operator builds the partitioned CSR inside every
query, as the CIDR design did. The edges arrive as (source, destination) row-id pairs from a join of the edge table
with its two vertex tables. The sink packs each edge into 64 bits, the destination range in the high bits, and
scatters it into its partition with \duckdb's radix partitioning, the same mechanism its hash join uses. There are at
least eight ranges, so that a small graph still gives eight tasks; the range width is a setting, and
Section~\ref{sec:eval-ablation} measures it. When the sink is done, tasks take the partitions largest first, sort each
partition's edges by source, emit its sparse rows and build its source index. The build costs 22, 128 and 264\,ms for
the 1.84, 18.7 and 55.7\,M edges of SF10, SF100 and SF300, which is the whole of a single-pair query (274 against
10\,ms over the index at SF300) and two fifths of a query for 1024 random pairs (1.3 against 0.77\,s).

Partitioning an adjacency by destination range, so that a traversal step writes only a cache-sized slice of the
vertices, is an established idea, known as CSR segmenting~\cite{zhang2017cagra} and propagation
blocking~\cite{beamer2017blocking}; GraphChi's shards partition edges by destination interval for the same
reason~\cite{kyrola2012graphchi}. Our layout differs in two respects. It is produced in one pass from a join stream inside a
relational operator, with radix partitioning and no per-vertex array, and the same layout, plus the row ids, is the
on-disk format of a transactional index (Section~\ref{sec:index}).

\subsection{Two traversals}
\label{sec:traversals}

A \emph{search} is one breadth-first search from one source. Before any search runs, the operator deduplicates the
sources. All pairs with the same source become one search, which carries the list of their destinations. A query
therefore has as many searches as it has distinct sources, and a search ends when it has reached every destination
on its list, at the depth bound, or when no new vertex is left to visit. The operator runs the searches in one of two
ways, each with a frontier of its own, or together as the lanes of a multi-source BFS. Both traversals proceed level by
level and decide per level between a \emph{sparse level}, which visits only the vertices on the frontier, and a
\emph{dense level}, which sweeps every sparse row of every partition.

\paragraph{Single-source traversal.} Each search has its own frontier, a vector of vertex ids, in the shape
Ligra~\cite{shun2013ligra} made standard, and records for every vertex the level at which it was first reached,
which is the vertex's distance. A sparse level, used while the frontier is smaller than a sixty-fourth of the
vertices, splits the frontier among the workers; each worker looks its vertices up in every partition through the
source index. A sparse level thus costs the frontier plus its edges. A dense level splits the partitions among the workers,
and a partition's rows as well when there are more workers than partitions; each worker expands the rows whose
source was reached on the previous level. In both cases two workers can reach the same vertex, and a vertex is
claimed with a compare-and-swap on a seen flag. The worker that wins records the vertex's distance, adds it to the
next frontier and, in the paths mode, records the vertex and the edge through which it arrived
(Section~\ref{sec:results}). A search holds 13 bytes per vertex while it runs, 25 in the paths
mode.

\paragraph{Multi-source traversal.} Many searches run as the lanes of one sweep, the multi-source BFS of Then et
al.~\cite{then2014msbfs}. A \emph{lane} is one search, and a \emph{batch} is up to 512 lanes that share one
\emph{working set}: three bit sets per vertex, the vertices each lane has seen, the current frontier and the next
one, 192 bytes per vertex at 512 lanes or 86\,MB at SF100. A level has two phases. The explore phase relaxes the
frontier into the next bit sets with one 512-bit \texttt{or} per edge for all lanes at once. In our measurements the
\texttt{or} is two 256-bit AVX2 instructions. The explore tasks are split by destination range; no two of them
write the same vertex, and the \texttt{or} needs no atomic. The check phase folds the next bit sets into the seen
bits; each lane then records the level of the destinations it has newly reached and drops them from its list, and a
lane whose list is empty is masked out of the frontier and stops spreading. A summary bitmap marks the vertices with
a live lane, and a level with fewer such vertices than a sixteenth of all vertices is sparse and visits only them,
through the source index. A dense level costs the same whether one lane or five hundred are alive.

The deduplication decides how many batches a query needs. LDBC BI19 at SF300 pairs every person of one city,
1.4\,K of them, with every person of another, and asks for 2.4\,M lengths. That is 1.4\,K searches in three batches;
one search per pair, as in the CIDR design, would have needed 4.6\,K batches. A pair whose source is unique is a
search with one destination. For the random pairs of Section~\ref{sec:eval}, almost all from different sources, the
deduplication changes nothing.

\subsection{Choosing a traversal and an orientation}
\label{sec:choice}

The finalize step groups the pairs by source and counts the groups. Up to 16 distinct sources run on the
single-source traversal, side by side, with the threads divided among them; more sources run as batches of the
multi-source traversal. Paths and reach always use the single-source traversal, because a path needs a parent per
vertex and reach returns a distance per vertex, and a lane keeps neither. A query that asks for the paths of many
sources therefore needs per-vertex arrays for each of its searches, the memory the lanes avoid
(Table~\ref{tab:traversal-choice}). \todo{rc8 runs the per-source searches in rounds within a memory budget and frees
a search's arrays when it ends (BI19 paths at SF300: 5.6\,GiB); describe from the code once it is merged.}

The orientation is decided before the grouping, from HyperLogLog estimates of the distinct sources and destinations
(64 registers, about 13\% error, enough for a threshold). When there are at least four times as many distinct sources
as destinations and reverse partitions are available, the searches start from the destinations and run over the
reverse partitions; the build route has reverse partitions only for an undirected graph, and paths and reach always
search forward. The reverse orientation pays
off when many sources share one destination, the shape of LDBC BI20, which then runs as a single search.

\subsection{Parallel execution as a chain of events}
\label{sec:phases}

A level is a parallel sweep followed by a short serial step that records what was reached and decides whether to
go on. The operator runs both traversals and the build as a \emph{chain of
per-phase events}. A phase is a set of tasks that run independently and finish; when the last one finishes, the
event's completion callback runs the serial step once and inserts the event of the next phase. The build is the sink,
which partitions the edges as they stream in, and one event, whose tasks sort and emit the partitions and whose
callback publishes them. A level of the multi-source traversal is two phases, the explore and the check phase, and a
level of the single-source traversal is one; a search that runs on a single thread runs all its levels in one task,
because an event per level would cost more than the level. Each phase still waits for the one before it, but no task
blocks its thread waiting for another task. \duckdb's own operators have this shape, and it lets the operator share
\duckdb's fixed thread pool with other queries. The scheduler may interleave the tasks of concurrent
queries freely, and an error or an interrupt stops the operator at the next task boundary.

\paragraph{Scheduling the batches.} The batches of a query run on \emph{worker groups}, at most one per thread; each
worker group runs one batch at a time and reuses its working set for the next. How many worker groups run at once is
decided by a memory budget of 512\,MiB. When the working sets of as many worker groups as threads fit the budget, they
all start at once and the bit sets stay in cache. Otherwise the scheduler starts 16 worker groups, doubles their number
while the throughput, in edges swept per second, rises by more than a tenth, and steps back when it falls by more than
a tenth. A worker group whose working set is at most a sixteenth of the budget has threads of its own; larger ones
pool their tasks, which keeps every thread busy while a worker group waits at the end of its level. A working set is zeroed
in parallel, and only when the next batch attaches it; a query with one small batch clears it once.

\paragraph{What stays serial.} The completion callbacks are serial by construction, and so is the grouping of the
pairs by source in the finalize step, which takes 6\,ms for 65\,536 random pairs at SF10 and about 30\,ms for BI19's
2.4\,M pairs at SF300. Everything that touches every pair or every vertex runs on all threads: the translation of
keys, the build, the levels and the emission of results (Section~\ref{sec:results}).

\subsection{Results}
\label{sec:results}

When the traversal is done, \duckdb runs the pipeline that reads the operator as its source, and the operator emits
one row per input row, in parallel over its output vectors. In the lengths mode each row looks up the distance its
source's search recorded for its destination, and a pair without a path gets \texttt{NULL}. In the reach mode each source emits every vertex it reached with its distance, and the destination table is
joined back afterwards only when the query projects its columns; the sources $\times$ all queries of
Section~\ref{sec:eval} run this way.

In the paths mode the operator returns, per pair, the list $[v_0, e_0, v_1, \dots, v_k]$ of vertices and edge row
ids. The scatter walks the parents a search recorded from the destination back to the source, maps vertex ids to row
ids on the build route and to keys on the index route, maps edge positions to row ids, and reverses the list.
\texttt{path\_length(p)} is then $\lfloor\text{len}/2\rfloor$, and \texttt{vertices} and \texttt{edges} are the even
and odd positions, which is also how the SQL fallback of \duckpgq defines them, so the build route returns the same
lists as the fallback. Because every edge position carries its row id when paths are asked for, a path can be joined
back to the edge table for its properties. Paths cost more than lengths when the pairs have many sources, because
paths need the single-source traversal; for 2048 random pairs over the index they take 3.6 times as long as lengths at
SF10 and 4.5 times at SF100. \todo{Single runs before rc5; confirm from the rerun.}
