\section{Conclusion and Lessons}
\label{sec:conclusion}
\label{sec:strategy}
\label{sec:hooks}
% Rewritten 12 Nov 2026: summary with its costs, then the lessons for an extension interface, then future work.

\rev{The CIDR version of \duckpgq answered shortest-path queries with UDFs, which inherit \duckdb's tuple-driven
parallelism, so a query with few pairs ran on one core and every query rebuilt the CSR. This paper removed both limits
without leaving the extension. The path-finding operator takes its parallelism from a CSR partitioned by destination
range and answers many pairs with one traversal, and its lead over Kuzu, Neo4j, Memgraph and FalkorDB grows with the
query. At SF300 it answers 1024 sources to every person in 773\,ms, against 21.9\,s for Kuzu, and 65\,536 pairs in
10\,s, where all four exceed ten minutes. The CSR index keeps the graph across queries and stays consistent with
\duckdb's MVCC through immutable epochs and a change log whose visibility \duckdb itself decides, once per change
group. Under sixteen readers and a writer a query over the index takes 82\,ms, against 3.9\,s with a CSR built per
query, and in all 5376 queries we compared, a transaction traversed exactly the edges it was allowed to see. The costs
are a single pair that is tens of milliseconds slower than Neo4j's bidirectional search, and a commit that waits for
the transactions that are building a snapshot.}

\rev{\duckdb's extension interfaces were enough to build both, and where they fell short the gaps are few. The index
callbacks report which rows changed but not which transaction changed them. The index therefore keeps no versions of
its own and asks \duckdb about visibility once per change group (Section~\ref{sec:index-interface}). Visibility can
be asked only for a live transaction, and a fold has to record what its epoch contains while its transaction runs
(Section~\ref{sec:index-fold}). The scheduler gives tasks to operators but not to indexes, and a fold runs inside
the query that triggers it. An extension operator can report a cardinality but not a cost, which leaves the choice
of traversal to a threshold inside the operator (Section~\ref{sec:choice}). A commit identifier passed with the index
callbacks, a visibility check that stays valid for past snapshots, and tasks for index work would remove the first
three. Two things the index relies on lie outside the promised interface, row ids that stay stable while an index
exists and the visibility check itself, which the index calls in \duckdb's transaction and table storage classes
(Section~\ref{sec:index-correctness}).}

\rev{In the future we will replace the thresholds of Sections~\ref{sec:choice} and~\ref{sec:index-fold} with a cost
model, starting with the few-sources limit, whose best value ranges from 2 to 64 sources across our graphs, and
report the operator's cost to the optimizer. We will also move the fold into the background, add a bidirectional
search for single pairs, and extend the operator to weighted shortest paths.}
