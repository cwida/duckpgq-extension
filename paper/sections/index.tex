\section{An MVCC-Consistent CSR Index}
\label{sec:index}

% Restructured 3 Nov 2026 around when the index pays off and its life cycle (build, change, read, fold, store),
% against the code at 9dfa2f98 and the vocabulary of paper/STYLE.md. Facts as audited on 3 Nov; numbers marked.

Without an index the operator builds the partitioned CSR inside every query. \texttt{CREATE INDEX knows\_csr ON
knows USING CSR (src, dst)} keeps it instead. \duckdb maintains the index across queries, transactions,
checkpoints and restarts, the rewrite of Section~\ref{sec:planner} uses it whenever the edge table has one, and every
transaction traverses exactly the edges it may see. This section first says when the index is worth having, then
what \duckdb's index interface offers it, and then follows the index through its life: how it is built and changed,
how a transaction reads it, how it is folded into a new version, and how it is stored. It ends with the argument and
the tests for its correctness.

\subsection{When the index pays off}
\label{sec:index-when}

The index saves the build, and the build is a fixed cost per query, 22, 128 and 264\,ms at SF10, SF100 and SF300
(Section~\ref{sec:csr}). For one heavy query that saving is small, because the traversal dominates; 65\,536 random
pairs at SF300 take a fifth less time over the index. For short queries it is the whole cost. A single pair at SF300
takes 28\,ms over the index and 284\,ms with the build, and because every query pays the build again, the gap grows
with the load. With 32 clients the index answers 323 single-pair queries per second at SF300 and the build 6, and
with 16 transactions reading under a writer a query takes 73\,ms over the index and 3.7\,s with the build, which also
holds the writer's commits back, 158 against 604\,ms. \todo{Probes of 30 Oct on rc9; the rerun's throughput and
concurrent steps replace them.} The index therefore pays off for workloads that run many queries over the same graph,
and helps a single heavy query little.

The index has four costs. It holds the graph in memory, about 11 bytes per edge of which 8 are the edge's row id,
617\,MB for the 55.7\,M edges of SF300. \todo{From the rerun's fixed-cost step.} Its overlay grows with the changes
since the last fold, and so does the time to build a snapshot, until a fold, a rebuild of the CSR from the table,
resets it; the transaction that triggers the fold pays for it, about 3\,s at SF300. \todo{Fold latency from the
rerun's SF300 fold step.} A transaction that has changed the edge table itself cannot use the shared index and builds
its own CSR, and for it the index saves nothing. And a table with the index keeps its deleted row ids instead of
compacting them (Section~\ref{sec:index-storage}). Commits are not slowed down. The index records a change in its log
and does no other work at commit, and a commit of 2000 edge changes costs 15\,ms with and without the index
(Section~\ref{sec:eval-updates}).

\subsection{What the interface gives, and what it withholds}
\label{sec:index-interface}

\duckdb's index interface, which the \texttt{vss} and \texttt{spatial} extensions also
use~\cite{duckdb_vss,duckdb_spatial}, provides five calls: (1) \emph{bulk build}, a parallel sink over the key columns
and row ids of the table that produces the initial index; (2) \emph{append}, called during every commit, once per
chunk of rows the transaction inserted, with their keys and row ids; (3) \emph{delete}, called the same way with the
rows the transaction deleted; (4) \emph{serialize}, which writes the index's bytes into \duckdb's block manager at a
checkpoint and into the write-ahead log; and (5) \emph{lookup}, with which the planner finds the index by table and
index name. Because \duckdb serializes commits, appends and deletes arrive in commit order. Each call holds a lock on
the index, which also protects the index's own state.

The interface withholds three things that a structure for traversals needs. The first is visibility. The calls carry
row ids and keys, never the transaction or the commit that made the change, and a transaction cannot ask the index
what it may see. An ART index does not need that, because it returns row ids that the table scan filters through the
row versions, one probe at a time; a traversal that touches ten million edges cannot afford a version check per edge.
The second is the past. \texttt{CanFetch(transaction, row)} answers whether a row is visible to a live transaction,
and only to a live one, because \duckdb garbage-collects a row version once no active transaction can observe it.
Visibility cannot be decided after the fact. The third is the vertex side. The index is attached to the edge table
and never learns the row ids of the vertex table, which are not stable without an index on that table. It therefore
identifies vertices by their key, as the \sqlpgq definition of the graph does, and edges by their row id in the edge
table. \duckdb changes row ids only when it compacts a table at a checkpoint, and it compacts only tables whose indexes
are all ARTs; with a CSR index present every row keeps its id. The one exception is a commit that fails after the
index has seen its append, for example on a unique-key conflict; \duckdb reverts the append and gives the same row ids
to the next insert. \todo{Not tested: whether a checkpoint that drops a fully deleted trailing row group also hands its
ids out again.}

Graph stores that own their transactions, LiveGraph and Teseo among them~\cite{zhu2020livegraph,deleo2021teseo}, keep
versions with every edge. That is not possible here, because no transaction or commit reaches the index. The versions
stay where \duckdb keeps them, in the table, and the index asks \duckdb about them once per group of changes.

\subsection{Building and changing the index}
\label{sec:index-structure}

\begin{figure}[t]
  \centering
  \input{figures/index_timeline}
  \caption{The index over time. Epoch 0 is the partitioned CSR of the edges visible to the transaction that built it
  (bound $b_0$); every later commit appends its change groups to the log, one per append or delete call, inserts in
  blue and deletes in red. A transaction takes the newest epoch its bound allows and decides once per group whether the
  group is visible to it. A fold rebuilds epoch 1 from the table as a transaction with bound $b_f$ sees it, which
  includes $g_1$ to $g_4$; epoch 0 stays until the next fold, for transactions that started before this one.}
  \label{fig:index-timeline}
\end{figure}

\texttt{CREATE INDEX} runs the bulk build and produces the first \emph{epoch}: the partitioned CSR of
Section~\ref{sec:csr} over every edge that the creating transaction can see, the \emph{dictionary} that maps vertex
keys to the dense ids the CSR uses, and the row id of every edge, next to its position (Figure~\ref{fig:index-timeline}).
An epoch is never modified. With \texttt{WITH (reverse = true)} the epoch also holds the reverse partitions, and an
index on an undirected edge table holds each edge in both directions.

Later changes go into a \emph{change log}. Each \texttt{Append} call adds one entry per inserted row, with its keys,
its row id and the ids the keys have in the current dictionary, and the entries of one call form a \emph{change group}.
Each \texttt{Delete} call forms a group as well. A deleted row that is in the log gets a \emph{stamp}, the number of
the deleting group, on its entry; a deleted row that the epoch contains gets a \emph{tombstone}, an entry that names
the row and carries its keys. When a row id arrives a second time, its first append was reverted by a failed commit,
and the index marks the earlier entry dead, visible to no transaction. The log stores no commit identifier,
transaction id or timestamp. Which entries a transaction may see is decided later, by \duckdb, when the transaction
reads the index.

\subsection{Reading the index}
\label{sec:index-read}

A transaction that runs a path query reads a \emph{snapshot}, the epoch plus an \emph{overlay} of the log. The overlay
has two parts: a bitmap of the epoch positions whose edges are deleted for this transaction, and the inserted edges it
may see, laid out in the same destination ranges as the epoch's partitions. A traversal step that processes one
epoch partition processes the inserted edges of the same range with it.

Which entries a transaction sees is decided by \duckdb, once per change group. The inserts of a group come from one
commit of one transaction, and they are visible to a transaction all or none; the transaction asks \texttt{CanFetch}
about one undeleted row of the group and knows the answer for the whole group. A delete group applies when one row it
deleted, whose insert the transaction sees, is no longer fetchable. Commits are serialized and groups are numbered in
commit order. A transaction therefore sees every group up to some point of the log, except the groups of failed commits,
which no transaction sees. The newest group it sees identifies its view, and the index caches the last snapshot it
built under the epoch, that group and a hash of the decisions made row by row (below); every transaction between two
commits receives the same snapshot. The version checks are paid even when the cached snapshot is returned, because the
cache key is computed from them.

Building the overlay costs one version check per group and one pass over the visible inserted edges, which places each
of them in its destination range. The entries carry their dictionary ids, and the pass needs no dictionary lookup per
edge; a key that is not in the epoch's dictionary, a new vertex, gets an id above the epoch's vertex count. A
tombstone is placed by a lookup from its keys, through the dictionary, the destination's partition, the source's
sparse row and the row id among its edges. In an undirected index the lookup also finds the mirrored edge, and both
directions are suppressed. Checking visibility per group instead of per entry keeps this cheap; one check per
log entry grew a single-source query at SF10 from 8 to 124\,ms as the pending changes accumulated
(Section~\ref{sec:eval-updates}). \todo{Pre-freeze number; from the rerun's per-row step.}

A transaction that has changed the edge table itself sees rows that no other transaction may see, and the log holds
only committed changes. Such a transaction builds a \emph{private epoch} from its own view of the table, a full build
inside its query, and nothing it builds is shared. The path of a pair over the index carries the row ids of its edges,
including edges inserted after the epoch, and the keys of its vertices (Section~\ref{sec:results}). It can therefore be
joined back to both tables without the index knowing their schemas.

\subsection{Folding the log into a new epoch}
\label{sec:index-fold}

The log grows with every commit and the overlay with it, so the index periodically builds a new epoch, a \emph{fold}.
A fold runs in a transaction without uncommitted changes of its own, at that transaction's bound $b_f$. It scans the
edges visible to the transaction, on one thread, builds the partitioned CSR with the parallel build of
\texttt{CREATE INDEX}, and installs the result as the newest epoch. It is started explicitly through a function, or
automatically by a transaction that, before building its snapshot, finds more log entries not yet in the newest epoch
than a configurable fraction of that epoch's edges, a tenth by default. The scan and the build run without holding the
index, which the fold takes only to check its trigger and to install the epoch; commits and other queries continue during
a fold. Folds are serialized. An automatic fold that finds another fold running does not wait for it, and its
transaction reads the current epoch and log; a fold whose transaction is not newer than the newest epoch does
nothing. Epochs are therefore installed in the order of their bounds. Section~\ref{sec:cost} discusses why the trigger
lies with the transactions and what a better policy would weigh.

The old epoch cannot be dropped at once. A transaction that started before the fold has a bound below $b_f$, and the
new epoch contains edges it must not see. The index keeps the previous epoch, a \emph{retained epoch}, until the next
fold, and serves each transaction from the newest epoch whose bound does not exceed its own. A transaction older than
both builds a private epoch. The log cannot be cleaned up by deciding visibility at $b_f$ after the fact, because the
row versions that would answer the question may be gone. Instead every epoch has a \emph{generation}, its number in
installation order, and the folding transaction records in every log entry the generation of the first epoch that
\emph{accounts for} it, by containing the inserted edge or excluding the deleted one. A snapshot of an epoch skips the
entries that epoch accounts for, and the log drops an entry once the oldest retained epoch accounts for it. A row that
a fold pulled into the new epoch and that is deleted afterwards gets both a stamp and a tombstone; transactions on the
older epoch see the delete through the stamp, transactions on the newer one through the tombstone. Entries that
resolved their keys against the older dictionary look their keys up again for the newer one.

\subsection{Checkpoint, recovery and load}
\label{sec:index-storage}

At a checkpoint the index writes the newest epoch and the log entries it does not account for through \duckdb's
index allocator, one block per segment, with a short manifest in the index's storage options; a checkpoint at which
the index has not changed reuses the stored blocks. The write-ahead log carries the same state in the record that
creates the index, and an index created after the last checkpoint survives a restart, and changes after the checkpoint
are replayed through \texttt{Append} and \texttt{Delete} like those of any index. An index is loaded on its first use.
The loader reads the stored blocks through \duckdb's block manager in rounds, deserializes the partitions in parallel
and returns the memory it freed to the system, in 0.03\,s at SF10 and 0.41\,s at SF300 (Table~\ref{tab:fixed-costs}).
\todo{Pre-freeze; from the rerun's fixed-cost step.}

Loaded entries lose two things until the next fold. They carry no change group, because after a restart every stored
row is committed, so their visibility is decided per row, and the snapshot cache key includes those decisions.
Loaded tombstones carry no keys and are placed by one parallel scan over the epoch's row ids. An index whose stored
format is missing or outdated, or that has a reverse side its stored state lacks, starts empty and rebuilds itself
from the table on first use. A table with a CSR index keeps the row ids of deleted rows until the index is dropped,
since \duckdb compacts only tables whose indexes are all ARTs.

\subsection{Correctness}
\label{sec:index-correctness}

Let $\mathit{Vis}(b)$ be the set of edge rows visible to a transaction with bound $b$, as \duckdb defines it through
\texttt{CanFetch}, and let epoch $E$ be built by a transaction with bound $b_e$, so $E = \mathit{Vis}(b_e)$. For a
transaction with bound $b \geq b_e$ the snapshot is $E \,\cup\, \Delta_b \setminus T_b$, where $\Delta_b$ are the inserted
rows of the groups visible to $b$ that $E$ does not account for, and $T_b$ the rows of the delete groups that apply to
$b$; we claim it equals $\mathit{Vis}(b)$. Every row inserted after $b_e$ reached the index through \texttt{Append} at
its commit, so $\mathit{Vis}(b) \subseteq E \cup \Delta$. A row of the log is in $\mathit{Vis}(b)$ exactly when its group
is visible to $b$, which covers rows inserted and deleted after $b_e$ and rows of failed commits, which are visible to
no transaction. A row of $E$ leaves $\mathit{Vis}(b)$ only through a delete that committed after $b_e$, and every such
delete reached \texttt{Delete} and became a stamp, a tombstone or both, whose group applies exactly when the delete is
visible to $b$. Entries appended to the log after the transaction copied its length belong to commits that cannot be
visible to the transaction, since \texttt{Append} runs during the commit, before the rows become visible.

Two retained epochs make the argument harder. A fold installs epoch $E'$ with bound $b_f$, and the claim holds for
$E'$ with $b_e := b_f$, because the fold records in each entry whether $E'$ accounts for it. An entry that $E'$
contains is left out of $\Delta$ for transactions on $E'$, so no edge is counted twice. The log drops an entry only once
the oldest retained epoch accounts for it, and every retained epoch still finds the entries it needs. A logged row that
$E'$ contains and that is deleted afterwards is removed through its stamp on the older epoch and through its tombstone
on $E'$. Groups decided per row enter the cache key through the hash of their decisions, and two transactions with
different views never share a snapshot. Private epochs are built from the transaction's own view and equal
$\mathit{Vis}(b)$ by construction.

The argument rests on three properties of \duckdb. Only the first, that the index calls happen at every commit and in
commit order, is part of the interface an extension is promised. The other two are behaviour of the current
implementation: that a row id is reused only after its append was reverted, and that \texttt{CanFetch} implements
$\mathit{Vis}$. Section~\ref{sec:hooks} counts these missing guarantees among the interface's gaps. Two properties are
ours. A reused row id marks the reverted entry dead, so $\Delta$ contains no row of a failed commit, and folds install
epochs in the order of their bounds, so a transaction is always served from the newest epoch its bound allows.

We test the claim in two ways. In the concurrent runs every reader transaction answers its query twice, over the index
and with a CSR built from the same transaction's view of the table, and the two answers must agree; the rc1 runs
compared 15\,765 transactions under a writer without a mismatch, and the rerun has a step that compares them with a fold
about every ten commits. \todo{Counts from rc10's check step.} Under the update stream all configurations, the index
with and without folds, the build and the four native systems, return the same answer after each of the 191 commits.
Fourteen regression test files cover the cases singled out above, among them two transactions that fold in either
order, a commit that fails after the index saw its append, deletes after a fold, deletes in an undirected index,
transactions that differ only in a fully deleted group, and checkpoints and restarts.

The argument does not cover a vertex deleted while its edges remain. The source and destination of a pair come from
the vertex tables, and a deleted source or destination yields no pair, but an intermediate vertex deleted with its
edges in place is still traversed, where the SQL rewrite would drop those edges through its join with the vertex
table. We document this as a semantic difference of the index. \texttt{CREATE INDEX} rejects keys that are not two
plain integer columns and a \texttt{UNIQUE} index, and a build fails for a graph with more than $2^{32}-1$ vertices.
