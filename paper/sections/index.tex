\section{An MVCC-Consistent CSR Index}
\label{sec:index}

% Restructured 3 Nov 2026 around when the index pays off and its life cycle (build, change, read, fold, store),
% against the code at 9dfa2f98 and the vocabulary of paper/STYLE.md. Facts as audited on 3 Nov; numbers marked.

A CSR index keeps the partitioned CSR of Section~\ref{sec:csr} between queries. It is created on the edge table
with \texttt{CREATE INDEX knows\_csr ON knows USING CSR (src, dst)}, and from then on it is an index like any other
in \duckdb: it follows every insert and delete of the edge table, it is written at checkpoints and recovered from the
write-ahead log, and it is used whenever a path pattern matches a table that has one. \rev{Without it, every query
rebuilds the CSR, 22\,ms at SF10 and 268\,ms at SF300 (Section~\ref{sec:eval-index}), a cost the index pays once.}
Unlike an index that returns row ids for the table to check, a
transaction traverses the CSR index in place, without consulting the table's row versions. The index must therefore
show a transaction the same graph that \duckdb's snapshot isolation would show it on the table. Section~\ref{sec:index-interface}
describes what \duckdb's index interface offers for this and what it withholds. Sections~\ref{sec:index-structure}
to~\ref{sec:index-storage} follow the index through its life, from the build and the changes that follow it, through
reading and folding, to checkpoint and recovery. Section~\ref{sec:index-correctness} \rev{states what that view rests on and how we test it}, and Section~\ref{sec:index-when} weighs the index's benefit against its costs.

\subsection{What the interface gives, and what it withholds}
\label{sec:index-interface}

\duckdb's index interface, which the \texttt{vss} and \texttt{spatial} extensions also
use~\cite{duckdb_vss,duckdb_spatial}, provides five calls: (1) \emph{bulk build}, a parallel sink over the key columns
and row ids of the table that produces the initial index; (2) \emph{append}, which \duckdb makes during a commit for
the rows the transaction inserted, one call per vector of up to 2048 rows, with their keys and row ids; (3)
\emph{delete}, made the same way for the rows the transaction deleted; (4) \emph{serialize}, which writes the index's
bytes into \duckdb's block manager at a checkpoint and into the write-ahead log; and (5) \emph{lookup}, with which the
planner finds the index by table and index name. \duckdb commits one transaction at a time, so the appends and deletes
of different commits never interleave, and each call holds the index's lock.

Three things the interface does not provide shape the design. It tells the index which rows changed but not
which transaction changed them. The calls carry row ids and keys, never a transaction or commit identifier, and the
index cannot record with an edge who is allowed to see it. The interface is built for indexes that return row ids and
leave the visibility check to the table scan, which filters each probe through the row's versions, and a traversal
over ten million edges cannot afford that check per edge. Nor can the index decide visibility later. The check
\duckdb offers, \texttt{CanFetch(transaction, row)}, answers only for a live transaction, because \duckdb
garbage-collects a row version once no active transaction can observe it. And the index learns about one table, the
edge table. It never sees the vertex table's row ids, so it identifies vertices by their key, the value a path pattern
compares anyway, and edges by their row id in the edge table. Row ids are stable while the index exists, because
\duckdb compacts a table's row ids only at a checkpoint and only when the table has no index other than an ART.

Graph stores that own their transactions, LiveGraph and Teseo among them~\cite{zhu2020livegraph,deleo2021teseo}, keep
a version with every edge. The interface rules that out, because it never gives the index a transaction id to store.
The versions instead stay in the table, and the index asks \duckdb about them once per group of changes.

\subsection{Building and changing the index}
\label{sec:index-structure}

\begin{figure}[t]
  \centering
  \input{figures/index_timeline}
  \caption{The index over time. Epoch 0 is the partitioned CSR of the edges that the transaction creating the index
  could see; it is never modified. Every later commit appends its change groups $g_1, g_2, \dots$ to the log, one
  group per append or delete call, inserts in blue and deletes in red. At $b_f$ a fold builds epoch 1 from the table
  (Section~\ref{sec:index-fold}). Each tick on the axis is a commit. The transactions below the axis show which epoch and which
  groups a transaction reads (Section~\ref{sec:index-read}).}
  \label{fig:index-timeline}
\end{figure}

\texttt{CREATE INDEX} runs the bulk build and produces the first \emph{epoch} (Figure~\ref{fig:index-timeline}): the
partitioned CSR of Section~\ref{sec:csr} over every edge that the creating transaction can see, the \emph{dictionary}
that maps vertex keys to the dense ids the CSR uses, and the row id of every edge, stored next to the edge's position.
\rev{A path found over the index therefore names its edges by row id and its vertices by key, as a path found over a
CSR built per query does (Section~\ref{sec:results}), and joins back to both tables.}
Created \texttt{WITH (reverse = true)}, the epoch also holds the reverse partitions, and an index on an undirected edge
table holds each edge in both directions.

An epoch is never modified. A CSR is packed and sorted, so inserting an edge would move every edge behind it, and
rebuilding the CSR at every commit would make each commit pay for the whole graph. Changes therefore go into a
\emph{change log}, which a commit only appends to; the work of applying them falls on the transactions that read the
index (Section~\ref{sec:index-read}). Each \texttt{Append} call adds one entry per inserted row, with its keys and
its row id, and the entries of one call form a \emph{change group}; a commit that inserts more than one vector of rows
makes several calls and therefore several groups. Each \texttt{Delete} call forms a group as well\rev{, and an update of a key column reaches the index as a delete
and an insert, as for any indexed column in \duckdb}. A deleted row that
is in the log gets a \emph{stamp}, the number of the deleting group, on its entry. A deleted row that the epoch
contains cannot be marked in the epoch, so it gets a \emph{tombstone}, an entry that names the row and carries its
keys. The log records nothing about which transaction or commit made a change; which entries a transaction may see is
decided when it reads the index.

\subsection{Reading the index}
\label{sec:index-read}

A transaction that runs a path query reads a \emph{snapshot}, the epoch plus an \emph{overlay} that corrects it for
the changes the transaction is allowed to see. The epoch stores its edges at fixed positions in its partitions
(Section~\ref{sec:csr}), and the overlay has two parts. The first is a bitmap with one bit per edge position, set
for the epoch edges that are deleted from the transaction's point of view. The second holds the inserted edges the
transaction is allowed to see, in a small CSR of their own with the same destination ranges as the epoch. A traversal step that processes the
epoch's partition of a range skips the suppressed positions and processes the inserted edges of the same range with
it.

Which changes a transaction is allowed to see is a question of \duckdb's snapshot isolation. A transaction sees the
rows that were committed before it started, and nothing that was committed later or never ($T_c$ in
Figure~\ref{fig:index-timeline} sees $g_1$ and $g_2$, $T_b$ sees all six groups). The index answers it with
\texttt{CanFetch}, once per change group. The edges of one group were inserted, or deleted, by one commit of one transaction, so a transaction sees either
all of the group's changes or none of them. For an insert group the index calls \texttt{CanFetch} on one of the
group's edges that has not been deleted since; the answer holds for the whole group. For a delete group it calls
\texttt{CanFetch} on one of the deleted edges whose insert the transaction sees; if that edge is no longer fetchable,
the transaction sees the whole delete group. Because commits are serialized and groups are numbered in commit order,
the groups a transaction sees are the first $n$ groups of the log for some $n$, except the groups of failed commits,
which no transaction sees.

This makes the snapshot cacheable. \rev{Two kinds of entry have no group to decide for them, the edges of an insert
group that were all deleted again and, after a restart, the loaded entries (Section~\ref{sec:index-storage}); the
index asks \texttt{CanFetch} about those per row. The key of a snapshot is the epoch, $n$ and the hash of those
per-row answers.} If the key equals that of
the snapshot built last, the transaction receives that snapshot, which is the usual case for every transaction that
starts between two commits. The \texttt{CanFetch} calls are therefore made even when the cached snapshot is returned.

Building the overlay costs one version check per group and one pass over the visible inserted edges, which places each
of them in its destination range. The entries carry their dictionary ids, and the pass needs no dictionary lookup per
edge; a key that is not in the epoch's dictionary, a new vertex, gets an id above the epoch's vertex count. A
tombstone is placed by a lookup from its keys, through the dictionary, the destination's partition, the source's
sparse row and the row id among its edges. In an undirected index the lookup also finds the mirrored edge, and both
directions are suppressed. The cost of a snapshot thus grows with the number of groups and inserted edges since the last fold, and not with
the number of log entries.

A transaction that has changed the edge table itself sees rows that no other transaction may see, and the log holds
only committed changes. Such a transaction builds a \emph{private epoch} from its own view of the table, a full build
inside its query, and nothing it builds is shared.

\subsection{Folding the log into a new epoch}
\label{sec:index-fold}

The log grows with every commit and the overlay with it, so the index periodically builds a new epoch from the
table, a \emph{fold} (epoch~1 in Figure~\ref{fig:index-timeline}). A fold runs inside an ordinary transaction without uncommitted changes, and the bound $b_f$ in the figure is
where that transaction started. \duckdb fixes a transaction's bound when the transaction starts, so the new epoch
holds the commits that transaction can see. The transaction scans the edges it can see (serially, an implementation shortcut; the parallel scan of
\texttt{CREATE INDEX} would apply unchanged), builds the
partitioned CSR with the parallel build of \texttt{CREATE INDEX}, and makes the result the index's newest epoch.
\todo{Desk measures the scan's share of the 3\,s SF300 fold after the Graphalytics block; then either parallelize
it or state the share here.} A fold
can be triggered explicitly, through a function, or automatically. Before a transaction builds its snapshot, it counts
the log entries that the newest epoch does not yet contain, and if they exceed a configurable fraction of that epoch's
edge count, a tenth by default, it folds first. That transaction pays for the fold, a scan and a build of the whole
graph, before its own query runs, about 1\,s at SF300 (Section~\ref{sec:index-when}); \todo{verify after rc13} the fold is not background
work. A transaction with uncommitted changes of its own never folds; it builds a private epoch instead
(Section~\ref{sec:index-read}). The scan and the build run without holding the index. The fold locks the index
twice, once to recount the log, so that two transactions that crossed the threshold at the same time do not both
fold, and once to make the new epoch the newest. Commits and other queries continue during a fold.
Folds are serialized; an automatic fold that finds another fold running does not wait, and its transaction reads the
current epoch and log instead. A fold whose transaction is older than the newest epoch does nothing, so the epochs
always follow the order of their bounds. Section~\ref{sec:cost} discusses why the trigger lies with the
transactions and what a better policy would weigh.

The new epoch does not replace the old one at once, because a transaction that started before the fold
(\mbox{$T_c$} in Figure~\ref{fig:index-timeline}) must not see the commits between its own start and $b_f$, which are visible in the
new epoch. The index therefore keeps the previous epoch as a \emph{retained epoch} until the next fold, two epochs at most,
and serves every transaction from the newest epoch whose bound is not after the transaction's own. A transaction that
started before both epochs were built gets neither and builds a private one.

With two epochs in use, the log cannot be truncated at a fold. A log entry is no longer needed once every retained epoch already
contains its inserted edge or already excludes its deleted one, which we call \emph{accounting for} the entry. An epoch
accounts for an entry when the entry's commit is visible at the epoch's bound. That cannot be computed later, because
\duckdb discards row versions once no live transaction needs them (Section~\ref{sec:index-interface}), so the folding
transaction records the answer while it is live. Every epoch has a \emph{generation}, its number in
the order the epochs were built, and the fold writes into each log entry the generation of the first epoch that
accounts for it.
From then on a snapshot of an epoch skips the entries that epoch accounts for, and the log drops an entry once the
oldest retained epoch accounts for it. Two cases need care. A row that the fold pulled into the new epoch and that is deleted afterwards gets both a
stamp and a tombstone, because transactions on the retained epoch find the row in the log and transactions on the new
epoch find it in the epoch. And the dictionary ids stored in a log entry (Section~\ref{sec:index-read}) belong to the
old epoch's dictionary; the new epoch has a dictionary of its own, so a snapshot of the new epoch looks the entry's
keys up again.

\subsection{Checkpoint, recovery and load}
\label{sec:index-storage}

The index persists like any other in \duckdb; rebuilding it after every restart would cost 4.8\,s at SF300
(Table~\ref{tab:fixed-costs}) before the first query. At a checkpoint it writes the newest epoch and the log entries that epoch
does not account for, through \duckdb's index allocator, one block per segment, with a short manifest in the index's
storage options. Only the newest epoch is written, because a retained epoch exists for running transactions, which a
restart ends. A checkpoint at which the index has not changed leaves the stored blocks in place. The write-ahead log carries the same state in the record that creates the index, so an index created after
the last checkpoint survives a restart, and the inserts and deletes committed after the checkpoint are replayed
through \texttt{Append} and \texttt{Delete} like those of any index.

An index is loaded on its first use after a restart, not when the database opens, because a database may hold
indexes its queries never touch. The loader reads the stored blocks through \duckdb's block manager in rounds of
bounded size and deserializes the partitions in parallel; the load takes 0.03\,s at SF10 and 0.41\,s at SF300 (Table~\ref{tab:fixed-costs}). \todo{Pre-freeze; from the
rerun's fixed-cost step.}

Loaded log entries lose two things until the next fold. The change groups are gone, and cannot be restored, because
after a restart every stored row is committed and the groups' commits are indistinguishable; the loaded entries are
therefore decided per row, with the row-by-row decisions in the snapshot cache key (Section~\ref{sec:index-read}).
Loaded tombstones carry no keys, so one parallel scan over the epoch's row ids places them. Both costs disappear at the first fold, which rebuilds the epoch and empties the log.

\subsection{Assumptions and tests}
\label{sec:index-correctness}

The argument of Sections~\ref{sec:index-structure} to~\ref{sec:index-storage}, that a transaction traverses over
the index the same edges a scan of the edge table would show it, rests on three properties of \duckdb. Only the first, that
the index calls happen at every commit and in commit order, is part of the interface an extension is promised. The other
two are behaviour of the current implementation. A row id is reused only after its append was reverted by a failed
commit, and \texttt{CanFetch} answers the visibility question snapshot isolation defines. Section~\ref{sec:hooks}
counts both among the interface's gaps.

We test the claim under concurrent writes by having every reader transaction answer its query twice, over the
index and with a CSR built from the same transaction's view of the table, and comparing the two; the results of these
runs are part of Section~\ref{sec:eval-updates}. Regression tests cover the cases of Sections~\ref{sec:index-read}
and~\ref{sec:index-fold}, among them folds in either order, a commit that fails after its append, deletes after a fold
and transactions that differ only in a fully deleted group.

The index \rev{route} differs from the \rev{build route} in one case, which we accept. Pairs come from the vertex tables, so a deleted
source or destination yields no pair, but an intermediate vertex deleted with its edges in place is still traversed;
the \rev{build route} would drop those edges through its join with the vertex table.

\subsection{When the index pays off}
\label{sec:index-when}

\rev{The build that the index saves is a fixed cost that depends on the graph alone, 22, 128 and 268\,ms at SF10,
SF100 and SF300, the gap between the two \duckpgq rows for one pair in Table~\ref{tab:random-pairs}. Because the cost
is fixed, its share of a query shrinks as the query grows.} For a single pair at SF300 the build is 96\% of the query,
278\,ms with the CSR built on the fly against 10\,ms over the index. For 65\,536 random pairs, whose traversal does
most of the work, the saving is 22\%, 2.8\,s of a 12.9\,s query. \todo{That gap is ten times the build; the desk
should say what else the build route pays at 65\,536 pairs before the rerun's numbers go in.} \rev{The index is
faster on every read-only point of Section~\ref{sec:eval}.} The first argument for
the index is therefore the workload of short queries, and it grows with the query rate because every query pays the
build again. With 32 clients the index answers 323 single-pair queries per second at SF300 and the on-the-fly build 6.

The second argument is concurrency. Readers share one index, each reading the snapshot its transaction is entitled
to, while a per-query build gives every reader its own CSR and every build competes for the same cores. The concurrent run of Section~\ref{sec:eval-updates} shows the
difference. With one writer committing 2000 edge changes every 200\,ms and 16 transactions querying single-source
distances at SF300, a query takes 73\,ms over the index and 3.7\,s with the on-the-fly build, and the builds also hold
the writer's commits back, 158 against 604\,ms. The index therefore pays off most for workloads with many short or concurrent queries over the same graph, and
least for a single heavy query, where it saves the build and no more.
