\section{An MVCC-Consistent CSR Index}
\label{sec:index}

% Revised 27 Oct 2026 against paper/STYLE.md; mechanics corrected against the code on 26 Oct and marked for the
% re-audit on the frozen commit. Numbers provisional.

Building the partitioned CSR costs 0.02 to 0.3\,s per query on our graphs (Section~\ref{sec:eval}), which is the
whole cost of a single-pair query and a fifth of a 65\,536-pair one (Table~\ref{tab:random-pairs}). The remedy is to keep the CSR, and the place
to keep it is an index. \texttt{CREATE INDEX knows\_csr ON knows USING CSR (src, dst)} asks \duckdb to maintain the
structure across queries, transactions, checkpoints and restarts, and its planner to use it when a path pattern
matches the edge table. This section describes what \duckdb's index interface gives such a structure, what it
withholds, and the design that follows from both.

\subsection{What the interface gives, and what it withholds}
\label{sec:index-interface}

\duckdb's index interface, which the \texttt{vss} and \texttt{spatial} extensions also
use~\cite{duckdb_vss,duckdb_spatial}, provides five things: (1) \emph{bulk build}, a parallel sink over the key columns
and row ids of the table that produces the initial index; (2) \emph{append}, called during every commit, once per chunk of
rows the transaction inserted, with their keys and row ids; (3) \emph{delete}, called the same way with the rows the
transaction deleted;
(4) \emph{serialize}, the index's bytes written into \duckdb's block manager at a checkpoint and into the write-ahead
log, replayed after a restart; and (5) \emph{lookup}, the planner finding the index by table and index name. \duckdb
serializes commits, so appends and deletes arrive in commit order, and each call runs under the index lock.

It withholds three things an index for traversals needs. The first is visibility. The calls carry row ids and keys,
never the transaction or the commit that made the change, and a transaction cannot ask the index what it may see. An
ART index does not need that, because it returns row ids that the table scan filters through the row versions, one
probe at a time. A traversal that touches ten million edges cannot afford a version check per edge, and it never goes
back to the table. The second is the past. \texttt{CanFetch(transaction, row)} answers whether a row is visible to a
live transaction, and only to a live one, because \duckdb garbage collects row versions as soon as no active
transaction can observe the earlier state, after which every row looks as if it had always been there. Nothing may be
decided retroactively. The third is the vertex side. The index is attached to the edge table and learns about its
rows; it never learns the row ids of the vertex table, and vertex row ids are not stable without an index on that
table either. The index therefore identifies vertices by their key, which is what the \sqlpgq definition of the graph
does anyway, and edges by their edge-table row id. Row ids are safe to store because \duckdb changes them only when it
compacts a table at a checkpoint, and it compacts only tables whose indexes are all ARTs; with a CSR index present
every row keeps its id until the index is dropped. There is one exception. A commit can fail after the index has
logged its append, for example on a unique-key conflict, and \duckdb then reverts the append and gives the same row
id to the next insert. The index sees the id appended a second time and marks the earlier entry dead, so no
transaction sees it. \todo{Not tested: whether a checkpoint that drops a fully deleted trailing row group also hands
its ids out again. If so, a reused id of an epoch row would bring the deleted edge back.}

\subsection{Epochs, change groups and snapshots}
\label{sec:index-snapshots}

\begin{figure}[t]
  \centering
  \input{figures/index_timeline}
  \caption{The index over time. Epoch 0 is the partitioned CSR of the edges visible to the transaction that built it
  (bound $b_0$); every later commit appends its change groups to the log, one per append or delete call, inserts in
  blue and deletes in red. A transaction takes the newest epoch its bound allows and decides once per group whether the
  group is visible to it. A fold rebuilds epoch 1 from the table as a transaction with bound $b_f$ sees it, which
  includes $g_1$ to $g_4$; epoch 0 stays until the next fold, for transactions that started before this one.}
  \label{fig:index-timeline}
\end{figure}

The design has three parts (Figure~\ref{fig:index-timeline}). An \emph{epoch} is an immutable partitioned CSR, with
the dictionary that maps vertex keys to dense ids and one edge-table row id per edge position, built by one
transaction and equal to the edge set that transaction could see. A \emph{change log} records every commit after the
epoch as one or more \emph{change groups}. An \texttt{Append} call becomes a group of inserted edges, each with its
keys, its row id and the ids the keys resolve to in the current dictionary. A \texttt{Delete} call becomes a group of
deleted rows, where a row that is in the log is stamped with the deleting group and a row that is in the epoch becomes
a tombstone. The log stores no commit identifier, transaction id or timestamp with an entry; what a transaction may see is
decided later, by \duckdb, when the transaction reads the log. A \emph{snapshot} is what a transaction that runs a path query traverses: the epoch
plus an overlay, which is a bitmap of suppressed epoch positions and a small adjacency of the inserted edges laid out
in the same destination-range partitions as the epoch, so that the traversal explores an epoch partition and its
companion in one step.

Visibility is decided by \duckdb, once per group. A group of inserts came from one commit of one transaction, so its
rows are visible to a transaction either all or none; the transaction asks \texttt{CanFetch} about one row of the group and
knows the answer for the whole group. A group of deletes applies when one row it deleted, whose insert the transaction
sees, is no longer fetchable. Commits are serialized, so the visible groups of a transaction form a prefix of the log, and
the newest visible group identifies which of them the transaction sees. The snapshot is therefore cacheable. The index
keeps the last snapshot it built, keyed by the epoch, the newest visible group and a hash of the decisions made per
row, because those rows are not covered by the newest group, and every transaction between two commits receives the
same one. A transaction with uncommitted changes of its own gets a private CSR built from its own view of the
table, a full build and not an overlay, because its view is its own and nothing it builds may be published. Building a
snapshot costs one version check per group since the fold, one pass over the inserted edges to bucket them by
destination range, and, once per new tombstone, a share of one parallel scan over the epoch's row ids that finds the
tombstone's position; the epoch's adjacency is not read. The version checks are paid even when the cached
snapshot is returned, because they are what identifies it. Groups whose rows have all been deleted again, and the log entries loaded with the index after a
restart, which carry no group, fall back to one check per row until the next fold. The per-row alternative, one version check per log entry, grew a single-source query at SF10 from 8 to 124\,ms as
the pending operations accumulated (Section~\ref{sec:eval-updates}), and is why change groups exist. \todo{Pre-freeze
number; the frozen matrix has no per-row visibility switch.}

Keys are resolved to dense ids when the group is appended, so that a snapshot can place inserted edges without a
dictionary lookup per edge. A key that is not in the epoch's dictionary, a new vertex, gets an id above the epoch's
vertex count at snapshot time. A fold rebuilds the dictionary in key order and a new smallest key shifts every id, so
each resolved id is tagged with the generation of its dictionary. A fold re-resolves the whole log against the new
dictionary, and a snapshot of an older retained epoch looks up the keys of entries tagged with another generation.

\subsection{Fold}
\label{sec:index-fold}

The log grows with every commit and the overlay with it, so a \emph{fold} periodically builds a new epoch. It is run
by a transaction without uncommitted changes of its own, with that transaction's bound $b_f$. It scans the edges
visible to it on one thread, builds the partitioned CSR with the same parallel build as \texttt{CREATE INDEX}, and installs the
result as the newest epoch; the log entries the new epoch contains are the ones visible at $b_f$. A fold is triggered
explicitly through a function, or automatically by the first transaction that finds the log larger than a configurable
fraction of the epoch, one tenth by default, before that transaction's snapshot is built. Folds are serialized by a lock, and a fold
does nothing when the newest epoch is at least as new as its transaction. Epochs are therefore installed in the
order of their bounds. Without the check, an older transaction that folds after a newer one would install its epoch
as the newest, and compaction would drop the log entries that only the newer epoch contains. The check also means
that when several transactions find the log too long at once, only the first rebuilds.
Section~\ref{sec:cost} discusses why the trigger belongs to the transaction side and what a policy should look at.

Two consequences of the interface shape the fold. The old epoch cannot be dropped at once, because a transaction that
started before the fold has a bound below $b_f$ and the new epoch contains edges it must not see. The index therefore
retains the previous epoch until the next fold, two epochs in all, and serves each transaction from the newest epoch
whose bound does not exceed its own. The log cannot be compacted by re-evaluating visibility at $b_f$ after the fact, because the
row versions that would answer the question are gone. Instead the folding transaction, while it is live, stamps every
log entry with the generation of the first epoch that accounts for it, and compaction drops the entries whose
generation is at most the oldest retained epoch's. Until then an entry stays in the log for the older epoch, and a
snapshot of the newer epoch skips it, so no edge is traversed twice. A transaction whose bound is older than every retained epoch, a long
transaction that started before two folds, gets no snapshot. Today its query fails with an error, and succeeds
when rerun in a new transaction; falling back to a build inside the query is the obvious fix.

\subsection{Checkpoint, recovery and load}
\label{sec:index-storage}

At a checkpoint the newest epoch and the log entries it does not account for are written through \duckdb's index allocator as a sequence of
one-block segments with a small manifest in the index's storage options. The write-ahead log carries the same
serialized state in the record that creates the index, so an index created after the last checkpoint survives a
restart with its epoch. Inserts and deletes that happened after the checkpoint are replayed through \texttt{Append}
and \texttt{Delete} like any other index and become change groups like any commit.
On opening the database the index is bound on its first use and loaded in parallel, partition by partition, in
0.03\,s at SF10 and 0.41\,s at SF300 (Table~\ref{tab:fixed-costs}, pre-freeze). Only an index whose stored format is missing or
outdated, or that has a reverse side its stored state lacks, comes up empty and rebuilds itself on first use. A table with a CSR index keeps its delete gaps until the
index is dropped, since \duckdb compacts row ids only for tables whose indexes are all ARTs; we document this as the
price of the design.

\subsection{Paths}
\label{sec:index-paths}

The epoch stores an edge-table row id per edge position and the log stores one per inserted edge, so a path
reconstructed by the single-source traversal (Section~\ref{sec:paths}) carries the row ids of its edges, including
edges inserted by the transaction itself, and vertex keys for its vertices. \texttt{edges(p)} can therefore be
joined back to the edge table for its properties, and \texttt{vertices(p)} to the vertex table by key, without the
index knowing either table's schema.

\subsection{Correctness}
\label{sec:index-correctness}

Let $\mathit{Vis}(b)$ be the set of edge rows visible to a transaction with bound $b$, as \duckdb defines it through
\texttt{CanFetch}, and let epoch $E$ be built by a transaction with bound $b_e$, so $E = \mathit{Vis}(b_e)$. For a
transaction with bound $b \geq b_e$ the snapshot is $E \,\cup\, \Delta_b \setminus T_b$, where $\Delta_b$ are the inserted
rows of the groups visible to $b$ and $T_b$ the rows of the delete groups that apply to $b$; we claim it equals
$\mathit{Vis}(b)$. Every row inserted after $b_e$ reached the index through \texttt{Append} at its commit, so
$\mathit{Vis}(b) \subseteq E \cup \Delta$. A row of the log is in $\mathit{Vis}(b)$ exactly when its group is visible
to $b$, which covers rows inserted and deleted after $b_e$ and rows of reverted commits, which are never visible to
anyone. A row of $E$ leaves $\mathit{Vis}(b)$ only through a delete that committed after $b_e$, and every such delete
reached \texttt{Delete} and became a tombstone or a stamp whose group applies exactly when the delete is visible to
$b$. Entries appended to the log after the transaction copied its length belong to commits that cannot be visible to the
transaction, since \texttt{Append} runs during the commit, before the rows become visible. The fold preserves the claim
with $b_e := b_f$. The argument rests on three invariants of \duckdb, that the hooks fire at every commit, that a row id
is reused only after its append was reverted, and that \texttt{CanFetch} implements $\mathit{Vis}$, and on two of
ours: a reused id marks the reverted entry dead, so $\Delta$ contains no row of a failed commit, and folds install
epochs in the order of their bounds, so the epoch a transaction is served from is the newest one its bound allows. What it does not
cover is a vertex deleted while its edges remain. The source and destination of a pair come from the vertex tables,
so a deleted source or destination yields no pair; an intermediate vertex deleted with its edges in place is still
traversed, where the SQL rewrite would have dropped those edges through its join with the vertex table. We document
this as a semantic difference of the index. \texttt{CREATE INDEX} rejects keys that are not
two plain integer columns and a \texttt{UNIQUE} index, and a build fails for a graph with more than $2^{32}-1$
vertices.
