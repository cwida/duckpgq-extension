\section{An MVCC-Consistent CSR Index}
\label{sec:index}

% Restructured 3 Nov 2026 around when the index pays off and its life cycle (build, change, read, fold, store),
% against the code at 9dfa2f98 and the vocabulary of paper/STYLE.md. Facts as audited on 3 Nov; numbers marked.

A CSR index keeps the partitioned CSR of Section~\ref{sec:csr} between queries. It is created on the edge table
with \texttt{CREATE INDEX knows\_csr ON knows USING CSR (src, dst)}, and from then on it is an index like any other
in \duckdb: it follows every insert and delete of the edge table, it is written at checkpoints and recovered from the
write-ahead log, and it is used whenever a path pattern matches a table that has one. Unlike an index that returns row ids for the table to check, a
transaction traverses the CSR index in place, without consulting the table's row versions. The index must therefore
show a transaction the same graph that \duckdb's snapshot isolation would show it on the table. Section~\ref{sec:index-interface}
describes what \duckdb's index interface offers for this and what it withholds. Sections~\ref{sec:index-structure}
to~\ref{sec:index-storage} follow the index through its life, from the build and the changes that follow it, through
reading and folding, to checkpoint and recovery. Section~\ref{sec:index-correctness} argues that the view is right and
says how we test it, and Section~\ref{sec:index-when} weighs the index's benefit against its costs.

\subsection{What the interface gives, and what it withholds}
\label{sec:index-interface}

\duckdb's index interface, which the \texttt{vss} and \texttt{spatial} extensions also
use~\cite{duckdb_vss,duckdb_spatial}, provides five calls: (1) \emph{bulk build}, a parallel sink over the key columns
and row ids of the table that produces the initial index; (2) \emph{append}, which \duckdb makes during a commit for
the rows the transaction inserted, one call per vector of up to 2048 rows, with their keys and row ids; (3)
\emph{delete}, made the same way for the rows the transaction deleted; (4) \emph{serialize}, which writes the index's
bytes into \duckdb's block manager at a checkpoint and into the write-ahead log; and (5) \emph{lookup}, with which the
planner finds the index by table and index name. \duckdb commits one transaction at a time, so the appends and deletes
of different commits never interleave, and each call holds the index's lock.

Three things the interface does not provide shape the design. It tells the index which rows changed but not
which transaction changed them. The calls carry row ids and keys, never a transaction or commit identifier, and the
index cannot record with an edge who is allowed to see it. The interface is built for indexes that return row ids and
leave the visibility check to the table scan, which filters each probe through the row's versions, and a traversal
over ten million edges cannot afford that check per edge. Nor can the index decide visibility later. The check
\duckdb offers, \texttt{CanFetch(transaction, row)}, answers only for a live transaction, because \duckdb
garbage-collects a row version once no active transaction can observe it. And the index learns about one table, the
edge table. It never sees the vertex table's row ids, so it identifies vertices by their key, the value a path pattern
compares anyway, and edges by their row id in the edge table. Row ids are stable while the index exists, because
\duckdb compacts a table's row ids only at a checkpoint and only when the table has no index other than an ART.

Graph stores that own their transactions, LiveGraph and Teseo among them~\cite{zhu2020livegraph,deleo2021teseo}, keep
a version with every edge. The interface rules that out, because it never gives the index a transaction id to store.
The versions instead stay in the table, and the index asks \duckdb about them once per group of changes.

\subsection{Building and changing the index}
\label{sec:index-structure}

\rev{\texttt{CREATE INDEX} runs the bulk build and produces the first \emph{epoch} (Figure~\ref{fig:index-timeline}): the
partitioned CSR of Section~\ref{sec:csr} over every edge that the creating transaction can see, the \emph{dictionary}
that maps vertex keys to the dense ids the CSR uses, and the row id of every edge, stored next to the edge's position.
Created \texttt{WITH (reverse = true)}, the epoch also holds the reverse partitions, and an index on an undirected edge
table holds each edge in both directions.}

\rev{An epoch is never modified. A CSR is packed and sorted, so inserting an edge would move every edge behind it, and
rebuilding the CSR at every commit would make each commit pay for the whole graph. Changes therefore go into a
\emph{change log}, which a commit only appends to; the work of applying them falls on the transactions that read the
index (Section~\ref{sec:index-read}). Each \texttt{Append} call adds one entry per inserted row, with its keys and
its row id, and the entries of one call form a \emph{change group}; a commit that inserts more than one vector of rows
makes several calls and therefore several groups. Each \texttt{Delete} call forms a group as well. A deleted row that
is in the log gets a \emph{stamp}, the number of the deleting group, on its entry. A deleted row that the epoch
contains cannot be marked in the epoch, so it gets a \emph{tombstone}, an entry that names the row and carries its
keys. The log records nothing about which transaction or commit made a change; which entries a transaction may see is
decided when it reads the index.}

\subsection{Reading the index}
\label{sec:index-read}

A transaction that runs a path query reads a \emph{snapshot}, the epoch plus an \emph{overlay} that corrects it for
the changes the transaction is allowed to see. The epoch stores its edges at fixed positions in its partitions
(Section~\ref{sec:csr}), and the overlay has two parts. The first is a bitmap with one bit per edge position, set
for the epoch edges that are deleted from the transaction's point of view. The second holds the inserted edges the
transaction is allowed to see, in a small CSR of their own with the same destination ranges as the epoch. A traversal step that processes the
epoch's partition of a range skips the suppressed positions and processes the inserted edges of the same range with
it.

Which changes a transaction is allowed to see is a question of \duckdb's snapshot isolation. A transaction sees the
rows that were committed before it started, and nothing that was committed later or never\rev{ ($T_a$ in
Figure~\ref{fig:index-timeline} sees $g_1$ to $g_3$, $T_b$ sees all six groups)}. The index answers it with
\texttt{CanFetch}, once per change group. The edges of one group were inserted, or deleted, by one commit of one transaction, so a transaction sees either
all of the group's changes or none of them. For an insert group the index calls \texttt{CanFetch} on one of the
group's edges that has not been deleted since; the answer holds for the whole group. For a delete group it calls
\texttt{CanFetch} on one of the deleted edges whose insert the transaction sees; if that edge is no longer fetchable,
the transaction sees the whole delete group. Because commits are serialized and groups are numbered in commit order,
the groups a transaction sees are the first $n$ groups of the log for some $n$, except the groups of failed commits,
which no transaction sees.

This makes the snapshot cacheable. The index computes a key from the epoch, $n$ and the \texttt{CanFetch}
answers for the edges that have no group to decide for them, the edges of an insert group that were all deleted again
and, after a restart, the loaded entries (Section~\ref{sec:index-storage}), hashed together. If the key equals that of
the snapshot built last, the transaction receives that snapshot, which is the usual case for every transaction that
starts between two commits. The \texttt{CanFetch} calls are therefore made even when the cached snapshot is returned.

Building the overlay costs one version check per group and one pass over the visible inserted edges, which places each
of them in its destination range. The entries carry their dictionary ids, and the pass needs no dictionary lookup per
edge; a key that is not in the epoch's dictionary, a new vertex, gets an id above the epoch's vertex count. A
tombstone is placed by a lookup from its keys, through the dictionary, the destination's partition, the source's
sparse row and the row id among its edges. In an undirected index the lookup also finds the mirrored edge, and both
directions are suppressed. The cost of a snapshot thus grows with the number of groups and inserted edges since the last fold, and not with
the number of log entries.

A transaction that has changed the edge table itself sees rows that no other transaction may see, and the log holds
only committed changes. Such a transaction builds a \emph{private epoch} from its own view of the table, a full build
inside its query, and nothing it builds is shared. The path of a pair over the index carries the row ids of its edges,
including edges inserted after the epoch, and the keys of its vertices (Section~\ref{sec:results}). It can therefore be
joined back to both tables without the index knowing their schemas.

\subsection{Folding the log into a new epoch}
\label{sec:index-fold}

The log grows with every commit and the overlay with it, so the index periodically builds a new epoch, a \emph{fold}\rev{ (epoch~1 in
Figure~\ref{fig:index-timeline})}.
A fold runs in a transaction without uncommitted changes of its own, at that transaction's bound $b_f$. It scans the
edges visible to the transaction, on one thread, builds the partitioned CSR with the parallel build of
\texttt{CREATE INDEX}, and installs the result as the newest epoch. It is started explicitly through a function, or
automatically by a transaction that, before building its snapshot, finds more log entries not yet in the newest epoch
than a configurable fraction of that epoch's edges, a tenth by default. The scan and the build run without holding the
index, which the fold takes only to check its trigger and to install the epoch; commits and other queries continue during
a fold. Folds are serialized. An automatic fold that finds another fold running does not wait for it, and its
transaction reads the current epoch and log; a fold whose transaction is not newer than the newest epoch does
nothing. Epochs are therefore installed in the order of their bounds. Section~\ref{sec:cost} discusses why the trigger
lies with the transactions and what a better policy would weigh.

The old epoch cannot be dropped at once. A transaction that started before the fold has a bound below $b_f$, and the
new epoch contains edges it must not see. The index keeps the previous epoch, a \emph{retained epoch}, until the next
fold, and serves each transaction from the newest epoch whose bound does not exceed its own\rev{ ($T_c$ in
Figure~\ref{fig:index-timeline} started before the fold and reads epoch~0)}. A transaction older than
both builds a private epoch. The log cannot be cleaned up by deciding visibility at $b_f$ after the fact, because the
row versions that would answer the question may be gone. Instead every epoch has a \emph{generation}, its number in
installation order, and the folding transaction records in every log entry the generation of the first epoch that
\emph{accounts for} it, by containing the inserted edge or excluding the deleted one. A snapshot of an epoch skips the
entries that epoch accounts for, and the log drops an entry once the oldest retained epoch accounts for it. A row that
a fold pulled into the new epoch and that is deleted afterwards gets both a stamp and a tombstone; transactions on the
older epoch see the delete through the stamp, transactions on the newer one through the tombstone. Entries that
resolved their keys against the older dictionary look their keys up again for the newer one.

\subsection{Checkpoint, recovery and load}
\label{sec:index-storage}

At a checkpoint the index writes the newest epoch and the log entries it does not account for through \duckdb's
index allocator, one block per segment, with a short manifest in the index's storage options; a checkpoint at which
the index has not changed reuses the stored blocks. The write-ahead log carries the same state in the record that
creates the index, and an index created after the last checkpoint survives a restart, and changes after the checkpoint
are replayed through \texttt{Append} and \texttt{Delete} like those of any index. An index is loaded on its first use.
The loader reads the stored blocks through \duckdb's block manager in rounds, deserializes the partitions in parallel
and returns the memory it freed to the system, in 0.03\,s at SF10 and 0.41\,s at SF300 (Table~\ref{tab:fixed-costs}).

Loaded entries lose two things until the next fold. They carry no change group, because after a restart every stored
row is committed, so their visibility is decided per row, and the snapshot cache key includes those decisions.
Loaded tombstones carry no keys and are placed by one parallel scan over the epoch's row ids. An index whose stored
format is missing or outdated, or that has a reverse side its stored state lacks, starts empty and rebuilds itself
from the table on first use. A table with a CSR index keeps the row ids of deleted rows until the index is dropped,
since \duckdb compacts only tables whose indexes are all ARTs.

\subsection{Correctness}
\label{sec:index-correctness}

The claim is that a transaction traverses the same edge set over the index that a table scan would show it. We
argue it informally, by case, and then say how it is tested; the argument depends on properties of \duckdb that are
named at the end. Let $\mathit{Vis}(b)$ be the set of edge rows visible to a transaction with bound $b$, as \duckdb
defines it through \texttt{CanFetch}, and let epoch $E$ be built by a transaction with bound $b_e$, so $E = \mathit{Vis}(b_e)$. For a
transaction with bound $b \geq b_e$ the snapshot is $E \,\cup\, \Delta_b \setminus T_b$, where $\Delta_b$ are the inserted
rows of the groups visible to $b$ that $E$ does not account for, and $T_b$ the rows of the delete groups that apply to
$b$; we claim it equals $\mathit{Vis}(b)$. Every row inserted after $b_e$ reached the index through \texttt{Append} at
its commit, so $\mathit{Vis}(b) \subseteq E \cup \Delta$. A row of the log is in $\mathit{Vis}(b)$ exactly when its group
is visible to $b$, which covers rows inserted and deleted after $b_e$ and rows of failed commits, which are visible to
no transaction. A row of $E$ leaves $\mathit{Vis}(b)$ only through a delete that committed after $b_e$, and every such
delete reached \texttt{Delete} and became a stamp, a tombstone or both, whose group applies exactly when the delete is
visible to $b$. Entries appended to the log after the transaction copied its length belong to commits that cannot be
visible to the transaction, since \texttt{Append} runs during the commit, before the rows become visible.

Two retained epochs make the argument harder. A fold installs epoch $E'$ with bound $b_f$, and the claim holds for
$E'$ with $b_e := b_f$, because the fold records in each entry whether $E'$ accounts for it. An entry that $E'$
contains is left out of $\Delta$ for transactions on $E'$, so no edge is counted twice. The log drops an entry only once
the oldest retained epoch accounts for it, and every retained epoch still finds the entries it needs. A logged row that
$E'$ contains and that is deleted afterwards is removed through its stamp on the older epoch and through its tombstone
on $E'$. Groups decided per row enter the cache key through the hash of their decisions, and two transactions with
different views never share a snapshot. Private epochs are built from the transaction's own view and equal
$\mathit{Vis}(b)$ by construction.

The argument rests on three properties of \duckdb. Only the first, that the index calls happen at every commit and in
commit order, is part of the interface an extension is promised. The other two are behaviour of the current
implementation: that a row id is reused only after its append was reverted, and that \texttt{CanFetch} implements
$\mathit{Vis}$. Section~\ref{sec:hooks} counts these missing guarantees among the interface's gaps. A reused row id is
the one case in which the index sees a row twice. A commit can fail after the index has logged its append, for example
on a unique-key conflict; \duckdb then reverts the append and gives the same row ids to the next insert. When the
index sees a row id it already holds, it marks the earlier entry dead, so $\Delta$ contains no row of a failed commit.
The second property of ours is that folds install epochs in the order of their bounds, so a transaction is always
served from the newest epoch its bound allows. \todo{Not tested: whether a checkpoint that drops a fully deleted
trailing row group also hands its ids out again.}

We test the claim in two ways. In the concurrent runs every reader transaction answers its query twice, over the index
and with a CSR built from the same transaction's view of the table, and the two answers must agree; the rc1 runs
compared 15\,765 transactions under a writer without a mismatch, and the rerun has a step that compares them with a fold
about every ten commits. \todo{Counts from rc10's check step.} Under the update stream all configurations, the index
with and without folds, the build and the four native systems, return the same answer after each of the 191 commits.
Fourteen regression test files cover the cases singled out above, among them two transactions that fold in either
order, a commit that fails after the index saw its append, deletes after a fold, deletes in an undirected index,
transactions that differ only in a fully deleted group, and checkpoints and restarts.

The argument does not cover a vertex deleted while its edges remain. The source and destination of a pair come from
the vertex tables, and a deleted source or destination yields no pair, but an intermediate vertex deleted with its
edges in place is still traversed, where the SQL rewrite would drop those edges through its join with the vertex
table. We document this as a semantic difference of the index. \texttt{CREATE INDEX} rejects keys that are not two
plain integer columns and a \texttt{UNIQUE} index, and a build fails for a graph with more than $2^{32}-1$ vertices.

\subsection{When the index pays off}
\label{sec:index-when}

The index saves rebuilding the CSR for every query, a fixed cost that depends only on the graph: 22, 128 and 264\,ms
at SF10, SF100 and SF300 (Section~\ref{sec:csr}). Whether that matters depends on the queries. One heavy query is
dominated by its traversal, and 65\,536 random pairs at SF300 take a fifth less time over the index. A short query is
dominated by the build, and a single pair at SF300 takes 28\,ms over the index against 284\,ms with it. Because every
query pays the build again, the difference grows with the load: with 32 clients the index answers 323 single-pair
queries per second at SF300 and the build 6, and with 16 transactions reading under a writer a query takes 73\,ms over
the index and 3.7\,s with the build, which also holds the writer's commits back, 158 against 604\,ms. The index
therefore pays off for workloads that run many queries over the same graph, and helps a single heavy query little. \todo{Probes of 30 Oct on rc9; the rerun's throughput and concurrent steps replace them.}

Its costs are the memory for the epoch, about 11 bytes per edge, of which 8 are the edge's row id; the overlay,
which grows with the changes since the last fold and with it the time to build a snapshot (one version check per
log entry instead of per group would have grown a single-source query at SF10 from 8 to 124\,ms over the update
stream of Section~\ref{sec:eval-updates}) \todo{pre-freeze number; from the rerun's per-row step}; and the fold itself, which
the transaction that triggers it pays for, about 3\,s at SF300. A table with the index also keeps its deleted row ids
instead of compacting them. Commits are not slowed down. The index records a change in its log and does no other work
at commit, and a commit of 2000 edge changes costs 15\,ms with and without the index
(Section~\ref{sec:eval-updates}). \todo{Bytes per edge and fold latency from the rerun.}
