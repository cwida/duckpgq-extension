\paragraph{Graph queries on relational systems}
Relational systems have answered graph queries for a long time, by rewriting pattern matching into joins over edge
tables~\cite{sun2015sqlgraph,jindal2014vertexica,fan2015grail}, by layering a graph query language on an
RDBMS~\cite{vanrest2016pgql}, and since SQL:2023 through \sqlpgq, the graph pattern matching part of the SQL
standard~\cite{deutsch2022gql}. \duckpgq~\cite{tenwolde2023duckpgq} took the third route as a \duckdb extension that rewrites \texttt{MATCH} into SQL;
this paper adds the two pieces we asked for there, a many-source path-finding algorithm and a compact graph
representation, and keeps them inside the extension. \rev{Other extensions bring graph queries to a relational system
without a path-finding operator of their own: Apache AGE adds Cypher to PostgreSQL~\cite{apacheage}, and pgRouting
builds a graph from a SQL query on every call and runs its algorithms over it~\cite{pgrouting}.} Systems that change
the engine itself add predefined joins and adjacency structures (GRainDB~\cite{jin2022graindb,jin2022predefinedjoins}),
worst-case optimal joins for cyclic patterns (EmptyHeaded~\cite{aberger2017emptyheaded}, Umbra~\cite{freitag2020wcoj})
or compressed adjacency indexes (GQ-Fast~\cite{lin2016gqfast}); their adjacency structures share the system's storage
and transaction code, where ours is a derived structure that an extension maintains through the public index
interface, which tells it neither which transaction committed a row nor what a transaction may see
(Section~\ref{sec:index}).

\paragraph{Path finding}
Variable-length and shortest-path patterns are the part of \sqlpgq that relational operators serve worst. A recursive
common table expression evaluates them as a chain of joins with one frontier table per step. RaSQL~\cite{gu2019rasql}
and the T\"ubingen work on recursion in SQL~\cite{hirn2019recursion} make that chain faster and keep its shape. We
take the other route, in the tradition of Grail~\cite{fan2015grail} and of in-database BFS
operators~\cite{jindal2014vertexica}, and build a compressed sparse row (CSR) layout to traverse. The traversal is multi-source BFS~\cite{then2014msbfs}, which runs as many searches as a register has bits through
one sweep over the adjacency, each search in a bit lane. \rev{Its cost per level is a sweep over all vertices whatever
the number of live lanes, which is the wrong cost for a single pair, and for few sources we run a single-source
traversal of the kind Ligra~\cite{shun2013ligra} made standard. Direction-optimizing BFS~\cite{beamer2012direction}
switches between pushing the frontier and pulling from the unvisited vertices on the frontier's size; our sparse and
dense levels switch on the same criterion between visiting the frontier through the source index and sweeping every
partition (Section~\ref{sec:traversals}).} The GraphBLAS~\cite{davis2019graphblas} expresses the same traversals as
sparse matrix products, and RedisGraph, now FalkorDB, is a graph database built on it~\cite{cailliau2019redisgraph}
that appears in our evaluation.

\paragraph{Native graph database systems}
Neo4j, Kuzu~\cite{feng2023kuzu}, TigerGraph~\cite{deutsch2019tigergraph} and Memgraph store adjacency lists as
their primary representation, so a shortest-path query never waits for a structure to be built. The price is a second
system next to the relational data, with its own storage, transactions and copy of the graph. Kuzu is the design
closest to ours, with columnar storage, vectorized execution and factorized intermediate results, and recursive joins
for variable-length patterns~\cite{feng2023kuzu}. \rev{Section~\ref{sec:eval} shows \duckpgq with the index tens of milliseconds behind Kuzu and Neo4j at one pair or one
source, one to two orders of magnitude ahead from a handful of sources on, and every update in the same transaction
as the tables.}

\paragraph{Dynamic and versioned graph structures}
Updating a CSR is the classic weakness of the layout, and a line of work replaces it with structures that absorb
edge updates: packed memory arrays and sparse arrays with gaps~\cite{wheatman2018pcsr,deleo2021teseo}, sorted
blocked adjacency lists~\cite{fuchs2022sortledton}, log-structured snapshots~\cite{macko2015llama}, and purely
functional trees that hand every transaction its own version~\cite{dhulipala2019aspen}. LiveGraph~\cite{zhu2020livegraph}
and Teseo~\cite{deleo2021teseo} add transactions with multi-version concurrency to such structures, and
Sortledton~\cite{fuchs2022sortledton} measures what versioning inside the structure costs. All of them own both the graph and its transaction manager; our index owns neither. \duckdb's row versions decide
what a transaction may see, and the index stores an immutable CSR per epoch and \rev{a change log classified per change
group}, which makes it closer to a materialized view than to a dynamic graph structure. The survey of streaming graph processing~\cite{besta2023dynamic}
and the experimental comparison of these structures~\cite{deleo2019pma} cover the design space we did not enter.

\paragraph{Indexes under MVCC}
An index in a multi-version system either stores version information per entry or, as PostgreSQL and \duckdb's
ART~\cite{leis2013art} do, stores only row identifiers and checks the row's versions on every
probe~\cite{wu2017mvcc,neumann2015mvcc}. A traversal that touches millions of edges cannot pay a version check per
edge. On LDBC SF10 that check alone grew a single-source query from 15 to 35\,ms as updates accumulated (Table~\ref{tab:updates}), so the index of
Section~\ref{sec:index} checks visibility once per change group and serves a
whole traversal from one immutable snapshot. It uses the index interface that \duckdb exposes to
extensions~\cite{duckdb2019}, the same hook the \texttt{vss} and \texttt{spatial} extensions
use~\cite{duckdb_vss,duckdb_spatial}. As far as we know it is the first snapshot-consistent graph structure built behind
such an interface, and Section~\ref{sec:conclusion} names what the interface would need to make it simpler.
