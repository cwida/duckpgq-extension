\section{Related Work}
\label{sec:related}

\paragraph{Graph queries on relational systems}
Relational systems answer graph queries by rewriting pattern matching into joins over edge
tables~\cite{sun2015sqlgraph,jindal2014vertexica,fan2015grail}, by layering a graph query language on an
RDBMS~\cite{vanrest2016pgql}, and since SQL:2023 through \sqlpgq~\cite{deutsch2022gql}.
Extensions bring graph queries to a relational system without a path-finding operator of their own: Apache AGE adds
Cypher to PostgreSQL~\cite{apacheage}, pgRouting builds a graph from a SQL query on every call and runs its algorithms
over it~\cite{pgrouting}, and the 2023 \duckpgq~\cite{tenwolde2023duckpgq} rewrites \sqlpgq's \texttt{MATCH} into SQL
with UDFs for the paths. Systems that change the engine add adjacency structures or predefined joins (GRainDB~\cite{jin2022graindb,jin2022predefinedjoins}, GQ-Fast~\cite{lin2016gqfast}) or worst-case optimal joins for cyclic patterns (EmptyHeaded~\cite{aberger2017emptyheaded}, Umbra~\cite{freitag2020wcoj}); their structures share the system's storage and transaction code, where ours is maintained through the public index interface (Section~\ref{sec:index}).

\paragraph{Path finding}
Variable-length and shortest-path patterns are the part of \sqlpgq that relational operators serve worst. A recursive
common table expression evaluates them as a chain of joins with one frontier table per step; RaSQL~\cite{gu2019rasql}
and the T\"ubingen work on recursion in SQL~\cite{hirn2019recursion} make that chain faster and keep its shape. We
take the other route, in the tradition of Grail~\cite{fan2015grail} and of in-database BFS
operators~\cite{jindal2014vertexica}, and build a CSR to traverse. The traversal is multi-source
BFS~\cite{then2014msbfs}, which runs as many searches as a register has bits through one sweep over the adjacency,
each search in a bit lane. Its cost per level is a sweep over all vertices whatever the number of live lanes, which is the wrong cost for a single pair. For few sources we therefore run a single-source traversal of the kind Ligra~\cite{shun2013ligra} made standard. Direction-optimizing BFS~\cite{beamer2012direction} switches between pushing
the frontier and pulling from the unvisited vertices on the frontier's size; our sparse and dense levels switch on the
same criterion between visiting the frontier through the source index and sweeping every partition
(Section~\ref{sec:traversals}). The GraphBLAS~\cite{davis2019graphblas} expresses the same traversals as sparse
matrix products, and RedisGraph, now FalkorDB, is a graph database built on it~\cite{cailliau2019redisgraph}.

\paragraph{Native graph database systems}
Neo4j, Kuzu~\cite{feng2023kuzu}, TigerGraph~\cite{deutsch2019tigergraph} and Memgraph store adjacency lists as
their primary representation, so a shortest-path query never waits for a structure to be built; the price is a second
system next to the relational data, with its own storage, transactions and copy of the graph. Kuzu is the design
closest to ours, with columnar storage, vectorized execution, factorized intermediate results and recursive joins for
variable-length patterns. Section~\ref{sec:eval} shows \duckpgq with the index tens of milliseconds behind Kuzu
and Neo4j at one pair or one source, one to two orders of magnitude ahead from a handful of sources on, and every
update in the same transaction as the tables.

\paragraph{Versioned graph structures and indexes under MVCC}
Updating a CSR is the classic weakness of the layout, and a line of work replaces it with structures that absorb
edge updates: packed memory arrays and sparse arrays with gaps~\cite{wheatman2018pcsr,deleo2021teseo}, sorted blocked
adjacency lists~\cite{fuchs2022sortledton}, log-structured snapshots~\cite{macko2015llama} and purely functional trees
that hand every transaction its own version~\cite{dhulipala2019aspen}; \citet{besta2023dynamic} survey the field and
\citet{deleo2019pma} compare the structures. LiveGraph~\cite{zhu2020livegraph} and Teseo~\cite{deleo2021teseo} add
multi-version transactions to such structures, and Sortledton~\cite{fuchs2022sortledton} measures what versioning
inside the structure costs; all of them own both the graph and its transaction manager. \rev{An index inside a multi-version database system owns neither, and it either stores version information per entry
or, as PostgreSQL and \duckdb's ART~\cite{leis2013art} do, stores only row identifiers and leaves the version check to
the scan that fetches the rows~\cite{wu2017mvcc,neumann2015mvcc}; the \texttt{vss} and \texttt{spatial} extensions
build HNSW and R-tree indexes behind \duckdb's index interface in the second way~\cite{duckdb_vss,duckdb_spatial}. A
traversal cannot afford a version check per edge (Section~\ref{sec:index-interface}), and our index is of a third kind,
an immutable CSR per epoch with a change log that \duckdb's row-version check classifies once per change group, closer
to a materialized view than to a dynamic graph structure. As far as we know it is the first snapshot-consistent graph
structure behind a general index interface; Section~\ref{sec:conclusion} names what the interface would need to make it
simpler.}
