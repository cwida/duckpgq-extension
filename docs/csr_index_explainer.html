The CSR index: snapshot-consistent adjacency under MVCC

How DuckPGQ keeps a packed compressed-sparse-row graph inside a DuckDB table index, so that a path-finding query traverses exactly the edges its transaction can see, while other transactions insert and delete edges, without storing a single commit id.

The index has three parts and one rule. An epoch is an immutable, partitioned CSR equal to the edge set that was visible when it was built. A delta is an append-only log of edges committed after that. Tombstones are an append-only log of epoch edges deleted after that. The rule, for a reader with visibility bound b at least the epoch's bound:

Vis(b)  =  epoch  ∪  { d ∈ delta : CanFetch(b, d.row) }  \  { t ∈ tombstones : ¬CanFetch(b, t.row) }

CanFetch is DuckDB's own row-visibility test. The index never records who committed what; it stores edge-table row ids, and DuckDB's version information decides what each reader sees. That is the whole trick, and it is why the index is correct under concurrent writers, explicit transactions and rollback (design doc, section 6).

2. Commits, change groups and what a reader sees

Every Append or TryDelete call the storage layer makes at commit time carries the rows of one commit chunk of one transaction. The index numbers these calls: a change group. All rows of a group share one visibility, so a reader decides a whole group by testing one of its rows with CanFetch. 3. Building a snapshot: the overlay

A snapshot is the epoch plus an overlay. The overlay has two parts: a bitmap over epoch edge positions for the tombstones that apply (suppression), and a small adjacency of the visible delta edges, sorted by source and bucketed by destination range exactly like the epoch partitions, so that every epoch partition has a companion delta partition. The traversal kernel visits an epoch partition, skips suppressed positions with one bit test per edge, then visits the companion. Delta edges to new vertices extend the id space above the epoch's vertex count.

Measured at LDBC SF10 (1.84 M edges, 32 threads): a single-source query with 1 024 destinations costs 19 ms on the index with no pending changes, 41 to 51 ms right after a commit with 267 k pending operations (the overlay is rebuilt once), and 23 ms for the next reader (cache hit). Before change groups the same query cost 80 to 130 ms because the overlay did one visibility check per pending row and two dictionary lookups per edge.

4. Folding: a new epoch

The delta and the tombstones grow with every commit. A fold builds a fresh epoch equal to the visible set at a new bound b_f and empties the logs. It is triggered when delta + tombstones > fold_ratio × epoch edges at the end of a query (default ratio 0.1), by CHECKPOINT, or by duckpgq_csr_index_fold(table, index).

5. Persistence and recovery

  • Checkpoint writes one byte stream: the newest epoch plus the log entries it does not account for, in fixed-size allocator segments; the segment list lives in the index's storage info. Writes during serialisation go to the main index under its lock. Each checkpoint rewrites the whole index.
  • Restart binds the index lazily from that stream: 90 ms for the 55.7 M-edge SF300 index on 32 threads (segments copied in parallel into uninitialised memory; the serial version took 1.15 s). WAL replay re-applies inserts and deletes through Append/Delete. Loaded entries carry no group and are decided per row until the next fold.
  • Row id stability. DuckDB only remaps row ids at vacuum when every index on the table is an ART; with a CSR index present, row ids are stable, so epoch positions keep pointing at the right rows. The table keeps delete gaps while the index exists.
  • An index created after the last checkpoint comes up empty, marks itself for rebuild, and the first snapshot performs the bulk build at that transaction's bound.

6. Paths through the index

Each epoch partition carries its edges' row ids and each delta edge carries its own, so a traversal that records, per discovered vertex, the edge it arrived through can return edges(p) as edge-table rows. Edges are packed as delta_flag << 63 | partition << 32 | offset; the result scatter resolves the row id through the partition's row-id array. Vertices come back as keys through the snapshot's dictionary. The same mechanism now works on the build-per-query route, where the row id travels as a third field of the endpoint struct through the radix build.
